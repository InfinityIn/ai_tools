# R1.4 — Спецификация фичи

## Назначение

Как фича описывается до кода: документ фичи, реестр функций, кто что ревьюит.
Уровень B: здесь рамка, раскладка реестра — в репозитории проекта.

## Границы

- **Решает:** spec → design → tasks, умирает с фичей; steering — отдельно; владелец
  ревьюит design, не PR.
- **Не решает:** не заменяет ADR (R2.2).

## Какую ошибку villas предотвращает

SDD-анализ в villas есть и работает, но требует телеметрию на 570 операций — обязательство,
которое выполнено на 26 из 570 и потому не исполняется.

## Содержание

> **ПЕРЕПИСАТЬ.** Ниже — действующий источник (villas `docs/specs/README.md`), принятый
> как есть. Решение владельца 23.09.2026: **SDD требует телеметрию на 570 операций,
> целевая — только под SLO (~30 операций)**. При переписывании этого регламента критерий
> готовности фичи сужается до операций под SLO (R6.2), остальное остаётся описанием,
> а не обязательством. Пока обязательство «фича без телеметрии не отгружена» действует
> в формулировке villas, регламент — `draft`.

### 1. Источник: spec-driven подход villas

Три семейства артефактов в одном репозитории: **спеки** (`docs/specs/` — реестр функций,
документы фич, аналитические ТЗ), **код** (`src/`, помеченный ID операций) и **тесты**
(помеченные теми же ID). Реестр **декларативный**: из него ничего не генерируется, он —
источник, на который ссылаются тесты, метрики, алерты и дашборды.

### 2. Три уровня реестра

- **Module** — способность продукта, не канал и не команда; новый модуль — через ADR.
- **Service** — функция, как её назвал бы владелец, конкретная по каналу («Авторизация
  на сайте» и «Авторизация в боте» — два сервиса).
- **User Operation** — шаг внутри сервиса, по которому можно сказать «сработало /
  не сработало».
- **Технический слой** (route, задача очереди, хендлер бота, контейнер) указывается
  строкой внутри операции, отдельного документа не имеет.

**Фича — не узел реестра.** Фича режется по модулям, поэтому фича — это документ
в `analysis/` со списком затронутых ID; карточка трекера ссылается на документ фичи,
документ — на ID.

### 3. Схема ID и правила изменения

- Сервис `MODULE-NN`, операция `MODULE-NN-NN`. ID выдаётся один раз и **не
  переиспользуется** после удаления узла (остаётся строка «удалён, причина»).
- Заголовок менять можно, ID — нет: на него ссылаются история проверок, метки метрик
  и селекторы тестов.
- Новая функция → сначала документ фичи (там выданы новые ID), потом файлы сервисов,
  потом код с метками. Смена смысла операции → старая помечается `выведена`, выдаётся
  новый ID. Правки реестра идут через ревью **вместе с кодом**.

### 4. Признак работоспособности и состояние

У каждой операции — три строки: **Сценарий** (вход → ожидаемый выход, за какое время),
**Сигнал** (какая телеметрия подтверждает), **Пороги** (что красит сервис). Если ни
сценария, ни сигнала нет — пишется **«не контролируется»** и одна строка, что нужно,
чтобы стало. Состояние узла: `в проде` / `за флагом` / `код написан, не выкачен` /
`не реализовано` / `выведен`. Состояние `код написан, не выкачен` заведено 06.09.2026,
потому что у `не реализовано` дежурному нечего чинить, а здесь — есть.

### 5. Критерий готовности фичи (в редакции villas — подлежит сужению)

Фича считается отгруженной, когда одновременно: код в проде и карточка ссылается на
документ фичи; **телеметрия отдаётся** (метрики с label `op="<ID>"`, события с исходом
и идентичностью, алерты и панели из раздела «Ожидаемая телеметрия»); файлы сервисов
обновлены; сценарная проверка лежит в репозитории и помечена ID.

**Целевая редакция (решение владельца 23.09.2026):** телеметрия обязательна **только
для операций под SLO** (~30), для остальных — описание в реестре без обязательства.
