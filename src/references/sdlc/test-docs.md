# Тест-документация (тест-анализ) — артефакты этапа

Справочник этапа «Тест-документация», стадия 05 — тест-анализ. Этап идёт через
**корпоративный контур**: источники требований живут в Jira, Confluence и Figma
(см. раздел «Корпоративный контур» ниже). Рабочий контур — `develop-it`
(`src/process/develop-it/SKILL.md`), разбор выгрузок — по правилам `analyze-it`;
регламенты — R1.1 (Definition of Ready), R4.1 (пирамида тестов и обязательные
ярусы), см. `docs/regulations/README.md`.

Этот файл описывает, **что должно быть на выходе этапа**. Как вести сессию —
в профильном скилле, не здесь.

## Граница этапа

| Делает этот этап (05) | Делает тест-дизайн (06) |
|---|---|
| Сбор данных из источников требований | Граничные значения, классы эквивалентности |
| Извлечение явных и неявных требований | Pairwise-наборы, матрица трассировки |
| Выявление противоречий и пробелов | План тестирования |
| User journeys | **Генерация тест-кейсов (Markdown + CSV)** |
| Разрешение замечаний | Сводка по тестам |
| **Не создаёт тест-кейсы** | Создаёт `test-cases.md`, `test-cases.csv` |

Тест-кейсы (`TC-001`, `TC-002`, …) создаются на стадии 06, не здесь. Этот этап
готовит требования — сырьё для дизайна.

## Вход

| Вход | Откуда | Обязателен |
|---|---|---|
| Бизнес-требования | сбор требований | да |
| ТЗ на постановку (`system-spec`) | системный анализ | да |
| Контракты API (`api-contracts`) | системный анализ | да |
| Артефакты архитектуры | архитектура | да |
| Предыдущие тестовые артефакты | прошлые прогоны, система управления тестированием | если функционал уже тестировался |
| Выгрузки источников требований | корпоративный контур (см. ниже) | в корпоративной среде |

Чего не хватает — называется конкретно, и работа не начинается: неполный вход
даёт неполный список требований, а дыру видно только на прогоне.

## Артефакты на выходе

| Артефакт | Файл | Обязателен |
|---|---|---|
| Список требований | `output/analyze/requirements-list.md` | да |
| Структура тест-документации | `output/analyze/test-docs-structure.md` | да |
| User journeys | `output/analyze/user-journeys.md` | да |
| Выявленные несоответствия | `output/analyze/issues-found.md` | да |
| Ответы на замечания | `output/analyze/issue-resolutions.md` | да |
| Изменения требований (для доработки) | `output/analyze/requirements-changes.md` | если фича уже тестировалась |
| Лог сессии сбора | `inputs/session-log.md` | да |
| Отчёт об изменениях фазы | `output/<фаза>/phase-changes-YYMMDDHHmm.md` | при повторном проходе |
| Сводный отчёт по фазам | `test-model-changes-YYMMDDHHmm.md` в корне задачи | при повторном проходе |

Сырьё сбора (выгрузки тикетов, страниц, макетов, результаты разбора изображений)
живёт в `inputs/collect/` и **не версионируется** — это эфемерные данные.

## Шаблон: requirements-list.md

```markdown
## REQ-BUS-001: Бизнес-требование
Описание: ...
Источник: <тикет / страница / макет>
Статус: явное / неявное / спорное

## REQ-FUN-001: Функциональное требование
## REQ-UI-001: Требование к интерфейсу
## REQ-NONFUN-001: Нефункциональное требование
```

## Критерии тестируемости требования

Каждое требование оценивается по пяти критериям; не прошедшее — в
`issues-found.md` с категорией **«тестируемость»**:

- **Атомарное** — описывает одну функцию или поведение, не составное.
- **Трассируемое** — имеет уникальную связь с бизнес-целью.
- **Тестируемое** — результат чёткий и измеримый: ожидаемый результат настолько
  конкретен, что **разные люди приходят к одному и тому же выводу**
  «пройден / провален».
- **Однозначное** — допускает только одно толкование.
- **Структурированное** — имеет чёткую и единообразную структуру.

Примеры плохо сформулированных требований:

- «Пользователь должен иметь возможность создавать новость» — неконкретно,
  неоднозначно, неатомарно.
- «Система должна корректно обрабатывать операцию создания новости» — что значит
  «корректно» и «обрабатывать»? Критических деталей нет.
- «Создание новости» со шагом «заполнить какими-то данными» — неполно,
  конкретных данных нет.

## Шаблон: test-docs-structure.md

Иерархия функционала **модуль → сервис → функция**; по ней на стадии 06
группируются тест-кейсы.

```markdown
# Структура тестовой документации

## Модуль: [Название]
### Сервис: [Название]
- Функция: [Название] → REQ-XXX, REQ-YYY
  - Связанные user journeys: UJ-001
```

## Шаблон: issues-found.md

Каждое замечание **обязано** содержать ссылку на конкретный файл и раздел с
цитатой в 3–5 строк контекста — читатель должен найти источник, не открывая
файлы.

```markdown
## ISSUE-001: <краткая формулировка расхождения>
- Источник А: `<файл>`, строка N, раздел «…»
  > «<цитата>»
- Источник Б: `<файл>`, таблица «…», строка «…»
  > «<цитата>»
- Расхождение: <в чём именно противоречие>
- Вопрос: <что нужно решить>
- Категория: противоречие / пробел / неоднозначность / тестируемость / орфография
- Статус: ожидает уточнения / разрешено
```

## Отчёты об изменениях между проходами

Фича редко проходит этап один раз. Чтобы повторный проход был виден, каждая
фаза кладёт рядом отчёт с таймстампом `YYMMDDHHmm`:

| Файл | Где | Назначение |
|---|---|---|
| `phase-changes-YYMMDDHHmm.md` | `output/<фаза>/` | что изменилось относительно предыдущего прохода этой фазы |
| `test-model-changes-YYMMDDHHmm.md` | корень задачи | сводка по всем фазам, **дополняется**, чужие разделы не трогаются |

```markdown
# Отчёт по изменениям фазы: <фаза>
Дата: YYYY-MM-DD HH:MM

## Статус
- Проход: первый / повторный
- Предыдущий отчёт: phase-changes-<timestamp>.md / отсутствует

## Изменения
### Добавлено
### Изменено
### Удалено

## Статистика
- Требований: N (+A добавлено, −B удалено, ~C изменено)
- Загружено источников: N
```

Первый проход — отчёт фиксирует, что артефакты созданы впервые. Повторный —
отчёт содержит разницу.

## Критерии приёмки этапа

- Список требований содержит **и явные, и неявные** требования; у каждого —
  код, источник и статус.
- Каждое требование проверено по **критериям тестируемости**; не прошедшие
  зафиксированы в `issues-found.md` с категорией «тестируемость».
- `test-docs-structure.md` создан: без иерархии модуль → сервис → функция
  тест-кейсы на стадии 06 не сгруппировать.
- User journeys описывают **основные и альтернативные** пути, включая обработку
  ошибок и отсутствие прав.
- Каждое замечание имеет источник с цитатой; **все критичные замечания
  разрешены** либо явно принято решение продолжать без ответов.
- Выполнена сверка на согласованность: тикет против страниц требований, макеты
  против описания, полнота сценариев.
- Выполнена проверка орфографии требований; найденное — в `issues-found.md`.
- Если фича уже тестировалась, старые артефакты найдены и сопоставлены с новыми
  требованиями — тест-кейсы адаптируются, а не пишутся заново.

## Типовые ошибки

- **Замечание без источника.** «Есть противоречие» без файла и цитаты
  невозможно проверить и невозможно закрыть.
- **Создание тест-кейсов здесь.** Стадия 05 готовит требования; кейсы — стадия 06.
- **Пропуск структуры тест-документации.** Следующая стадия остаётся без
  группировки и делает плоский список кейсов.
- **Только happy path в user journeys.** Пустые данные, отказ интеграции и
  отсутствие прав не попадут в покрытие.
- **Требование без источника.** Через месяц невозможно понять, откуда оно и
  действует ли ещё.
- **Копирование артефактов между стадиями.** Следующая стадия читает файлы из
  `output/` напрямую; копии расходятся.

## Корпоративный контур

Этап опирается на внешние корпоративные системы — вне такой среды он работает
по локальным материалам, положенным в `inputs/`.

| Источник | Что даёт | Куда ложится |
|---|---|---|
| Jira | тикет задачи, критерии приёмки, связи, вложения; поиск связанной тестовой задачи по связи «Tested by» | `inputs/collect/issue_<KEY>/` |
| Confluence | страницы требований, таблицы, макросы | `inputs/collect/page_<ID>/` |
| Figma | макеты: UI-элементы, комментарии, экспорт PNG | `inputs/collect/figma/<file_key>/` |
| Разбор изображений | визуальные требования из макетов и скриншотов | `inputs/collect/image_analyzer/` |

Дополнительно: **система управления тестированием** — оттуда читаются
существующие тест-кейсы для контекста; перенос новых артефактов в неё выполняет
человек по регламенту.

Правила работы с этим контуром:

- Сырьё выгружается на диск, в работу идут сводки.
- Разбор изображений запускается **только после подтверждения списка файлов**
  человеком; иконки меньше 128×128 px исключаются.
- Реестр внешних ссылок (`inputs/collect/resource_registry.json`) — единый:
  по нему видно, какие ссылки уже обработаны, а какие ждут.
- При появлении новых источников после ответов на замечания тест-анализ
  повторяется целиком, а не только по новым файлам.
