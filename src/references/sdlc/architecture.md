# Архитектура — артефакты этапа

Справочник этапа «Архитектура». Рабочий контур — `develop-it`
(`src/process/develop-it/SKILL.md`), выбор технологии — `research-it`;
регламенты — R2.1 (принципы архитектуры), R2.2 (ADR: решение до реализации),
R2.6 (границы модулей и деплой-юниты), дополнительно R2.3 и R2.4,
см. `docs/regulations/README.md`. Частично корпоративный контур: репозиторий
архитектуры организации и материализация контекста из Jira/Confluence
(см. «Корпоративный контур» ниже).

Этот файл описывает, **что должно быть на выходе этапа**. Как вести сессию —
в профильном скилле, не здесь.

## Артефакты на выходе

| Артефакт | Файл | Когда обязателен |
|---|---|---|
| Резюме решения | `output/architecture-overview.md` | всегда |
| ADR | `docs/adr/NNNN-<slug>.md` | на каждое значимое решение (R2.2) |
| C4 (Context / Container / Component) | `output/c4.md` | новый модуль или новые границы |
| ERD | `output/erd.md` | меняется модель данных |
| Схема БД | `output/db-schema.md` | меняется модель данных |
| Соглашения об интеграции | `output/integration-agreements.md` | есть внешние взаимодействия |
| Sequence-диаграммы | `output/sequence-diagrams.md` | нетривиальные сценарии интеграции |

Диаграммы — в Mermaid, текстом в репозитории: конструкция вместо картинки
(R2.1). Создаются только релевантные фиче файлы; неактуальные пропускаются с
пометкой в `architecture-overview.md`.

## Классификация задачи

Состав артефактов определяется типом работы — это решение фиксируется в
`architecture-overview.md`:

1. **С нуля** — новый модуль: полный набор (C4, ERD, схема БД, интеграции).
2. **Изменение существующего модуля** — дельта «было / стало», перечень
   затронутых интеграций и таблиц.
3. **Без изменений** — требования укладываются в существующие сервисы и
   таблицы: только `architecture-overview.md` с обоснованием, остальное
   пропускается с пометкой.

## Шаблон: architecture-overview.md

```markdown
# Архитектура: <title>

## 1. Классификация (с нуля / изменение / без изменений) и обоснование
## 2. Размещение в модели системы (модуль, слой, деплой-юнит)
## 3. Как закрываются требования тикета (требование → элемент решения)
## 4. Принятые решения и отвергнутые варианты (со ссылками на ADR)
## 5. Модель данных — что добавляется/меняется
## 6. Интеграции и контракты
## 7. Proof of Concept (если проводился) — что проверено и чем
## 8. Риски, ограничения, открытые вопросы
```

## Критерии приёмки этапа

- **ADR написан до реализации, а не задним числом** (R2.2): контекст, варианты,
  решение, последствия, дата, статус.
- **Артефакты согласованы друг с другом**: ERD ↔ схема БД ↔ C4 ↔ соглашения об
  интеграции ↔ sequence-диаграммы. Сверка выполняется **не автором артефактов**.
  Несверенные артефакты не считаются готовыми.
- Нет компонентов без владельца данных и интеграций без описанного контракта и
  поведения при ошибке.
- Зависимости идут **только вниз по слоям** (`channels → catalog → domain →
  platform`) и проверяемы автоматически, например `import-linter` (R2.6).
- Каждый архитектурный принцип, заявленный в решении, имеет **автопроверку** —
  тест, линтер или гейт (R2.1). Принцип без сторожа не соблюдается.
- Цифры о текущей системе (объёмы, кардинальности, доли) **подтверждены дважды**;
  вывод без цифры уходит в «непроверенное».
- Версии, лимиты и цены внешних технологий взяты из живых источников (≥2
  независимых, со ссылкой и датой), а не из памяти модели.

## Типовые ошибки

- **ADR задним числом.** Решение принято в коде, документ дописан через месяцы —
  альтернативы уже не рассматриваются (R2.2).
- **Артефакты, противоречащие друг другу.** Имя таблицы в ERD не совпадает со
  схемой БД, связь есть на C4 и отсутствует в интеграциях.
- **Принцип без сторожа.** «Слои не зависят вверх» без `import-linter` держится
  до первого срочного релиза (R2.1).
- **Интеграция без описания отказа.** Таймаут, ретраи и поведение при
  недоступности не описаны — их не будет в коде.
- **Диаграмма картинкой.** Схема, которую нельзя сдиффить, устаревает молча.
- **Деление на слишком много деплой-юнитов.** Границы модулей выбираются под
  зависимости, а не под число сервисов (R2.6).

## Корпоративный контур

В корпоративной среде этапу дополнительно нужны:

- **Репозиторий архитектуры организации** — куда человек переносит согласованные
  модули и изменения. Артефакты этапа пишутся в `output/`, перенос выполняет
  человек по регламенту, не сессия.
- **Jira / Confluence** — материализация контекста задачи: связанные страницы,
  смежные тикеты, паспорта модулей. Сырьё кладётся на диск, в работу идут сводки.
- **Профиль организации** (например, разные инсталляции одного продукта) — от
  него зависит, в какой репозиторий и какую кодовую базу пойдёт решение.

Без этих систем этап работает по локальным материалам о текущей системе.
