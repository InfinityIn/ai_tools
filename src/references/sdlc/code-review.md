# Проверка кода — артефакты этапа

Справочник этапа «Проверка кода». Рабочий контур — `develop-it`
(`src/process/develop-it/SKILL.md`); регламенты — R4.4 (код-ревью),
R4.3 (сторожа и мутации), R3.2 (малые изменения),
см. `docs/regulations/README.md`.

Этот файл описывает, **что должно быть на выходе этапа**. Как вести сессию —
в профильном скилле, не здесь.

## Артефакты на выходе

| Артефакт | Файл | Обязателен |
|---|---|---|
| Отчёт проверки кода | `output/code-review-report.md` | да |
| Вердикт | раздел отчёта | да |
| Подтверждение мутацией по тестам из диффа | раздел отчёта | если в диффе есть тесты |

Вход этапа — **локальные изменения git** (staged и unstaged, ещё не
запушенные), ТЗ на постановку и контракты API. Если изменений нет — этапа нет.

## Шаблон: code-review-report.md

```markdown
# Отчёт code review: <title>

## Область ревью (ветка, диапазон изменений, файлы)

## Вердикт
<мержить | мержить после правок | не мержить>

## Замечания
### Критичные (блокируют)
- <severity> — <файл:строка> — <проблема> — <вход → неверный выход> — <рекомендация>
### Важные
### Незначительные / стиль
### Не подтверждено (проверка не воспроизвела)

## Соответствие ТЗ и контрактам API
## Безопасность
## Честность тестов (мутационная проверка)
## Итог и рекомендация
```

## Фиксированный список аспектов

Проверка ведётся по закрытому списку, чтобы охват не зависел от настроения
(R4.4). Каждый аспект проверяется **независимо от находок остальных**:

1. **Соответствие требованиям и контрактам API** — что из ТЗ не реализовано, что
   разошлось с контрактом.
2. **Корректность и граничные случаи** — логика, null и пустые значения,
   конкурентность, транзакции, обработка ошибок.
3. **Безопасность** — инъекции, авторизация и доступы, секреты, валидация ввода,
   логирование чувствительных данных.
4. **Производительность** — запросы в цикле, отсутствующие индексы, поведение на
   объёме, блокировки.
5. **Читаемость и сопровождаемость** — конвенции проекта, дублирование, мёртвый
   код, имена, документация.

Находки дедуплицируются: одна проблема — одна запись, с самым высоким из
присвоенных severity.

## Критерии приёмки этапа

- **Проверяет не автор кода** (R4.4). Автор своих ошибок не видит по построению.
- **Каждое замечание уровня major и выше подтверждено вход → неверный выход**:
  конкретные данные и путь исполнения. Замечание без такого доказательства
  попадает в раздел «не подтверждено», а не в блокирующие.
- **Подтверждение перемером своей выборкой**: цифры из отчёта разработчика
  пересчитываются, а не переписываются.
- **Честность тестов доказана мутацией** (R4.3): проверяемое поведение ломается
  намеренно, тест обязан упасть. Тест, не падающий на заведомо сломанном коде,
  ничего не проверяет — это находка уровня major.
- Вердикт — **ровно один из трёх**: мержить / мержить после правок / не мержить.
  «В целом нормально» вердиктом не является.
- Область ревью ограничена изменениями git; разведка связанного кода — в
  пределах затронутых модулей, без сканирования проекта целиком.

## Типовые ошибки

- **Замечание без воспроизведения.** «Тут может быть null» без входа и пути
  исполнения — шум, который съедает доверие к отчёту.
- **Ревью автором.** Самопроверка находит стиль и не находит логику.
- **Подстрока вместо утверждения.** Проверка «в выводе есть слово ok» проходит
  на сломанном коде (R4.3).
- **Вердикт без списка правок.** «Мержить после правок» без перечня с
  `файл:строка` не исполним.
- **Расширение ревью на весь проект.** Побочные находки оформляются отдельными
  задачами, а не раздувают текущий отчёт (R3.2).
- **Код поправлен вместо замечания.** Этап даёт анализ и рекомендации; правки
  делает разработка.

## Корпоративный регламент

Если у команды есть свой регламент код-ревью — политика одобрения, площадка,
распределение проверяющих, список важных мест по направлениям — он имеет
приоритет над шаблоном выше. Импортированный корпоративный регламент —
в `code-review/corporate-code-review-policy.md` рядом с этим файлом.
