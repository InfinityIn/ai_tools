# Разработка (код) — артефакты этапа

Справочник этапа «Разработка». Рабочий контур — `develop-it`
(`src/process/develop-it/SKILL.md`); регламенты — R3.1 (цикл фичи), R3.2 (малые
изменения), R3.3 (стиль, линтеры, типы), R3.4 (обработка отказов),
дополнительно R3.5 (гигиена веток и рабочих деревьев),
см. `docs/regulations/README.md`.

Этот файл описывает, **что должно быть на выходе этапа**. Как вести сессию —
в профильном скилле, не здесь. Профили этапа: `development-backend.md`,
`development-frontend.md`.

## Вход

| Вход | Откуда | Обязателен |
|---|---|---|
| ТЗ на постановку (`system-spec`) | системный анализ | да |
| Контракты API (`api-contracts`) | системный анализ | если фича трогает API |
| Артефакты архитектуры: C4, ERD, схема БД, соглашения об интеграции | архитектура | да |
| Дизайн-макеты (выгрузки Figma в `inputs/`) | этап дизайна | если в составе работ есть фронтенд |
| `intent.md` — замечания и ограничения разработчика | собирается в диалоге | да |
| Исходный код системы | открытый проект | да |

**Артефакты предыдущих этапов читаются по ссылке из `manifest.artifacts`
(из их `output/`), а не копированием.** Если они лежат в другом репозитории или
задаче — это тот момент, где нужен человек: пути указываются в
`.sdlc/<slug>/config.yaml` или напрямую.

Перед началом должно быть определено: целевой репозиторий и **область**
(модули и каталоги задачи — чтобы не сканировать проект целиком), тип изменения
(новый модуль или правка существующего) и **состав работ** — бэкенд, фронтенд
или оба. Состав неизвестен — его называет человек, а не догадка.

**Порядок при смешанном составе:** сначала бэкенд (контракты и данные —
фундамент), затем фронтенд. Фронтенд может стартовать на моках до готовности
API, но финальная приёмка — на реальном API.

## Артефакты на выходе

| Артефакт | Где | Обязателен |
|---|---|---|
| Код в ветке `feature/<slug>` | открытый проект | да |
| Тесты реального пути вызова | открытый проект | да |
| План с разбиением на work-items | рабочий файл этапа | да |
| Changelog этапа | `output/changelog.md` | да |
| Миграции БД | репозиторий проекта | если меняется схема |

Changelog **один на стадию** и **дописывается, а не перезаписывается**: файла
нет — создать по шаблону, файл есть — добавить свой раздел, чужие не трогать;
свой раздел уже есть (повторный прогон) — обновить его, а не дублировать.

## Шаблон: changelog.md

```markdown
# Changelog: <title>

## Состав работ (бэкенд / фронтенд / оба)

## Реализовано
- <изменение> — <файлы/модуль> — <суть>

## Изменения в БД / миграции
## Точки интеграции
## Тесты (что покрыто, где лежат, как запускать)
## Расхождения с ТЗ и принятые решения
## Что осталось / TODO
```

## Шаблон: план (work-items)

План составляется **до кода** и согласуется:

- перечень изменений, разбитый на **небольшие самостоятельные work-items** в
  порядке выполнения; где можно — независимые друг от друга;
- затрагиваемые файлы и модули по слоям, изменения в БД и миграции, точки
  интеграции;
- **как каждый пункт будет проверен** (сборка, конкретный тест);
- риски и открытые вопросы.

Нарезка на work-items — не формальность: пункт должен быть самодостаточным
(ясная граница, проверяемое «готово») и независимым по файлам. Состояние
(чек-лист, принятые решения) живёт в файле на диске, а не в голове.

## Критерии приёмки этапа

- **Красный тест реального пути вызова написан до кода** и зафиксирован в
  changelog: красный → зелёный (R3.1). Зелёный вспомогательный метод — не
  зелёная фича.
- Тесты **честны**: выборочная мутация ломает проверяемое поведение, и тест
  падает. Тест, не падающий на заведомо сломанном коде, — дефект (R4.3).
- **Код собирается после каждого work-item.** Несобирающийся код не готов.
- Изменение — **один класс задачи на PR**, без попутных правок «раз уж я здесь»
  без воспроизведённого отказа (R3.2).
- **Нет молчаливого best-effort**: проглоченных исключений нет, каждый отказ
  либо виден, либо помечен явной функцией отказоустойчивости с метрикой (R3.4).
- Линтеры и типы (`ruff`/`mypy`/`tsc`/`eslint` — по стеку) проходят и **запускаются
  в гейте**, а не только локально (R3.3).
- Дифф вычитан **не автором work-item** до передачи на проверку кода.
- Перед мержем проверено состояние **всех рабочих деревьев**, не только текущего
  (R3.5).
- Реализация совпадает с ТЗ и контрактами API; расхождение оформлено замечанием,
  а не подгонкой.

## Интеграционная сборка (когда состав работ смешанный)

Если задачу закрывали и бэкенд, и фронтенд, стадия не считается закрытой, пока
не пройдена интеграционная сборка:

- Система собрана и поднята **целиком**; пройден **сквозной сценарий из ТЗ на
  реальном API, не на моках**.
- **Источник правды — документация** (контракты API и системные требования).
  Расхождение реализации с ней оформляется **формализованным замечанием в адрес
  виновной стороны**: ожидание по документации → фактическое поведение, как
  воспроизвести. **Подгонка под факт запрещена.**
- Изменение самой документации — **только возвратом на системный анализ**.
- Если расхождение блокирует сквозную проверку, этот пункт уходит в «Что
  осталось / TODO», остальная приёмка продолжается.
- Changelog на стадию **один**: профиль дописывает свой раздел, чужие не трогает;
  при повторном проходе свой раздел обновляется, а не дублируется.

## Типовые ошибки

- **Реализация разошлась с контрактом молча.** Контракт — источник правды;
  расхождение исправляется возвратом на системный анализ (R2.3).
- **Одна волна правок на тысячи строк.** Ревью такого диффа не находит дефектов;
  дробить на малые изменения (R3.2).
- **Выдуманный API или файл.** Сигнатура «по памяти» вместо сверки с кодом.
- **Проглоченное исключение.** `except: pass`, `catch {}`: замер villas —
  **406 из 439 исключений проглочены** (R3.4, см. `docs/regulations/README.md`).
- **Тест на вспомогательную функцию.** Реальный путь вызова не покрыт.
- **Прогресс только в контексте сессии.** Длинная сессия теряет чек-лист —
  состояние обязано лежать в файле.

## Границы этапа

Этап **не пишет формальную тест-документацию QA** (это `test-docs.md` и
`test-design.md`) и **не заменяет независимую проверку кода** (`code-review.md`).
Артефакт этапа в `output/` — changelog, а не копия кода.
