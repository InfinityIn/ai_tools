# Тестирование (прогон) — артефакты этапа

Справочник этапа «Тестирование». Рабочий контур — `develop-it`
(`src/process/develop-it/SKILL.md`); регламенты — R4.1 (пирамида тестов),
R4.3 (сторожа и мутации), R5.3 (приёмка на проде),
см. `docs/regulations/README.md`.

Этот файл описывает, **что должно быть на выходе этапа**. Как вести сессию —
в профильном скилле, не здесь.

## Вход

Тест-кейсы из тест-дизайна, ТЗ на постановку (для трактовки ожидаемого
поведения), выгрузка итогов прогона (логи автотестов, отчёты). Автотесты, если
они были написаны на этапе разработки, лежат в открытом проекте.

## Артефакты на выходе

| Артефакт | Файл | Обязателен |
|---|---|---|
| Инструкции по запуску | `output/run-instructions.md` | да |
| Отчёт о прогоне | `output/test-run-report.md` | да |
| Баг-репорты | `output/bug-reports/BUG-<n>.md` | на каждый подтверждённый дефект |

Этап идёт в два такта: сначала **инструкции** (как запустить), затем — после
фактического прогона — **разбор итогов** и баг-репорты.

## Шаблон: run-instructions.md

Команды и шаги запуска: автоматические тесты (по ярусам), интеграционные,
ручные кейсы. Для каждого блока — окружение, подготовка данных, команда,
ожидаемое время и как понять, что прогон завершился успешно.

## Шаблон: test-run-report.md

```markdown
# Отчёт о прогоне: <title>

## Область прогона (окружение, сборка, набор кейсов)
## Итог: всего / пройдено / упало / заблокировано
## Покрытие кейсов (какие выполнены, какие пропущены и почему)
## Разбор падений (кейс → симптом → причина → доказательство)
## Заведённые баг-репорты
## Вывод и рекомендация
```

## Шаблон: BUG-<n>.md

```markdown
# BUG-<n>: <краткое название>
- Связанный тест-кейс: TC-<n>
- Серьёзность: blocker | critical | major | minor
- Окружение:
- Шаги воспроизведения:
- Фактический результат:
- Ожидаемый результат:
- Логи / артефакты:
```

## Критерии приёмки этапа

- Каждый выполненный кейс имеет статус; **пропущенные кейсы имеют причину**, а
  не молча отсутствуют.
- Каждое падение разобрано: дефект продукта, дефект теста или дефект данных —
  вывод подкреплён строкой лога или скриншотом.
- Баг-репорт **воспроизводим**: шаги, данные, окружение и сборка названы;
  фактический и ожидаемый результат разведены.
- Ожидаемый результат берётся **из ТЗ и кейса**, а не из того, как система себя
  ведёт сейчас.
- Приёмка пользовательских сценариев — на собранном приложении, **экран целиком
  и в реальном браузере** (R5.3); проверка пути записи подтверждается повторным
  чтением данных, а не только ответом API.
- Отчёт содержит явный вывод: можно ли отдавать, что блокирует.

## Типовые ошибки

- **«Упало — значит флака».** Нестабильность объявлена без повторного прогона и
  без разбора; реальный дефект уезжает в прод.
- **Баг без шагов.** «Не работает кнопка» не воспроизводится и возвращается
  автору.
- **Ожидание, подогнанное под факт.** Кейс переписан под текущее поведение —
  дефект узаконен.
- **Зелёный прогон при нуле собранных тестов.** Набор не собрался, отчёт
  зелёный (R4.2).
- **Тест, который не падает.** Проверка на подстроку проходит и на сломанном
  коде (R4.3).
- **Проверка только по ответу API.** Изменение пути записи не проверено повторным
  чтением — «исправление» ничего не исправило (R5.3).

## Границы этапа

Этап **не пишет тест-кейсы** (это тест-дизайн) и **не правит код**:
подтверждённые дефекты уходят формализованными баг-репортами обратно в
разработку.
