# Системный анализ — артефакты этапа

Справочник этапа «Системный анализ». Рабочий контур — `develop-it`
(`src/process/develop-it/SKILL.md`); регламенты — R1.4 (спецификация фичи),
R2.3 (контракты: единственный источник и генерация), R2.4 (модель данных и
миграции), см. `docs/regulations/README.md`.

Этот файл описывает, **что должно быть на выходе этапа**. Как вести сессию —
в профильном скилле, не здесь.

## Артефакты на выходе

| Артефакт | Файл | Обязателен |
|---|---|---|
| ТЗ на постановку | `output/system-spec.md` | да |
| Контракты API | `output/api-contracts.md` (+ OpenAPI-фрагменты) | если фича трогает API |
| Видение аналитика (сырьё) | `inputs/intent.md` | да |

Вход этапа: бизнес-требования, артефакты архитектуры, действующие системные
требования, ссылка на макеты. Артефакты предыдущих этапов читаются **по ссылке**
из их `output/`, а не копированием — копии расходятся с оригиналом.

## Шаблон: system-spec.md

```markdown
# ТЗ на постановку: <title>

## 1. Контекст и ссылки на требования/архитектуру
## 2. Системные требования (функциональные)
## 3. Логика работы (сценарии, бизнес-правила, состояния)
## 4. Модель данных и изменения в БД
## 5. Интеграции и зависимости
## 6. Нефункциональные требования
## 7. Влияние на существующую систему
## 8. Открытые вопросы и риски
```

## Шаблон: api-contracts.md

Для каждого эндпоинта/метода: путь и метод, назначение, запрос (поля, типы,
обязательность, валидация), ответ (схема, примеры), **коды и тела ошибок**,
идемпотентность, права доступа, пагинация и сортировка. Где уместно —
фрагменты OpenAPI.

**Контракт — источник правды, а не черновик** (R2.3). Реализация обязана
совпасть с контрактом; расхождение исправляется возвратом на этот этап, а не
подгонкой кода или документа под факт.

## Критерии приёмки этапа

- Каждое системное требование **ссылается на код бизнес-требования** —
  непокрытых требований нет, лишних требований без источника нет.
- Состояния сущностей описаны **явной машиной состояний**: перечень состояний,
  триггеры, таблица допустимых и недопустимых переходов (R2.4). `NULL` не
  используется как состояние.
- Статусы и периоды описаны как перечисления, а не как свободные строки (R2.4).
- Контракт описывает **и ошибки тоже**: коды, тела, поведение потребителя.
- Раздел «Влияние на существующую систему» называет конкретные модули, таблицы и
  интеграции, а не «возможно, затронет».
- Пробелы и неоднозначности вынесены в «Открытые вопросы», а не закрыты догадкой.

## Типовые ошибки

- **Контракт руками в нескольких местах.** Одна и та же структура описана в ТЗ,
  в коде бэкенда и в типах фронтенда — копии расходятся молча. Контракт
  описывается один раз, остальное генерируется (R2.3).
- **Постановка без модели данных.** «Добавить поле» без типа, обязательности,
  значения по умолчанию и плана миграции — дефект на этапе разработки (R2.4).
- **Фильтр, описанный только словами.** Условие выборки без единой спецификации
  расходится между SQL и кодом.
- **Сценарий без альтернатив.** Описан только happy path; пустые данные, отказ
  интеграции, отсутствие прав не описаны — их не будет ни в коде, ни в тестах.
- **Копирование чужих артефактов в свой `inputs/`.** Плодит дубли и размывает
  канон; читать нужно по ссылке.

## Границы этапа

Этап **не проектирует архитектуру** (это предыдущий этап) и **не пишет код**.
Артефакт — документ; перенос контрактов в репозиторий контрактов выполняет
человек по регламенту.
