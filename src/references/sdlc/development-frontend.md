# Разработка: фронтенд — дельта артефактов этапа

Справочник этапа «Разработка», профиль фронтенда. Рабочий контур — `develop-it`
(`src/process/develop-it/SKILL.md`); регламенты — R2.3 (контракты как
единственный источник), R3.1 (цикл фичи), R5.3 (приёмка на проде: экран целиком,
реальный браузер), см. `docs/regulations/README.md`.

Общие артефакты и критерии этапа — в `development.md`. Здесь только **дельта
фронтенда**: она ничего не отменяет, а добавляет.

## Вход

Тот же, что у этапа в целом (`development.md`, раздел «Вход»), с уточнением по
обязательности:

| Вход | Откуда | Обязателен |
|---|---|---|
| **Контракты API (`api-contracts`)** — источник правды | системный анализ | да |
| ТЗ на постановку (`system-spec`) | системный анализ | да |
| Дизайн-макеты — выгрузки Figma в `inputs/` | этап дизайна | да, если макеты есть |
| Артефакты архитектуры | архитектура | по необходимости |
| `intent.md` — замечания и ограничения разработчика | собирается в диалоге | да |
| Исходный код системы | открытый проект | да |

Артефакты предыдущих этапов читаются **по ссылке из `manifest.artifacts`**, а не
копированием. Фронтенд может стартовать до готовности API — на моках, — но
финальная приёмка идёт на реальном API.

## Дополнительные артефакты

| Артефакт | Где | Когда обязателен |
|---|---|---|
| Раздел фронтенда в `output/changelog.md` | `output/changelog.md` | всегда |
| Формализованные замечания к бэкенду | changelog, раздел расхождений | есть расхождение с контрактом |
| Перечень расхождений с макетом | changelog | есть макеты |
| Отметка, что проверялось на моках | changelog | использовались моки |

## Документация — источник правды

Источник правды — **контракты API и системные требования**, а не то, что сегодня
отдаёт стенд (R2.3). Порядок при расхождении реального бэкенда с документацией:

1. Зафиксировать **формализованное замечание в адрес бэкенда**: что именно
   расходится (эндпоинт, поле, формат, код ответа), **ожидание по документации →
   фактическое поведение**, как воспроизвести.
2. Передать замечание владельцу и в задачу бэкенду.
3. **Продолжать работу по документации.**

**Подгонять фронтенд под фактическое поведение, расходящееся с документацией, —
запрещено:** молчаливая подгонка прячет дефект бэкенда и ломает следующего
потребителя. Менять саму документацию фронтенд не может — только возвратом на
системный анализ.

Если расхождение блокирует проверку живьём, приёмка **этого** work-item
откладывается: пункт уходит в «Что осталось / TODO» вместе с замечанием,
остальная работа продолжается.

## Макеты

Вёрстка сверяется с макетом: состав элементов, состояния, отступы, поведение при
разных размерах. Результат сверки — **перечень расхождений**, а не пересказ
макета. Расхождение «макет против ТЗ» решает владелец.

## Проверка живьём — обязательна

- Приёмка только на **собранном приложении в браузере**, **экран целиком**, а не
  по коду и не по одному компоненту (R5.3).
- **CSR-страницы проверять только в реальном браузере.** Встроенная панель без
  отображения может не композитить кадры и не запускать data-запросы: **пустой
  экран у наблюдателя ≠ пустой экран у пользователя**. Вывод «не работает»
  делать только после проверки в реальном браузере.
- Проверяются консоль и сетевые запросы, а не только картинка.

## Состояние, маршрутизация, доступность

Загрузка, пустое состояние, ошибка, права доступа, маршруты и deep links,
клавиатура и фокус, контраст — **явные пункты плана**, а не «поправлю по ходу».
Что не попало в план — не сделано.

## Моки

Моки бэкенда допустимы, пока API не готов, и должны быть **помечены и
отключаемы**. **Финальная приёмка — на реальном API**; changelog фиксирует, что
именно проверялось на моках.

## Критерии приёмки дельты

- Экран проверен целиком в реальном браузере, консоль чистая, сетевые запросы
  соответствуют контракту.
- Все состояния экрана (загрузка, пусто, ошибка, нет прав) реализованы и
  проверены — каждое было пунктом плана.
- Моки отключены или явно перечислены в changelog вместе с тем, что на них
  проверялось.
- Расхождения с контрактом оформлены замечаниями, а не «подкручены» в коде.
- Вёрстка сверена с макетом; расхождения перечислены и решены владельцем.

## Типовые ошибки

- **Подгонка под стенд.** Код подстроен под фактический ответ — дефект бэкенда
  зафиксирован в двух местах вместо одного.
- **Приёмка по коду.** «Компонент выглядит правильно» вместо проверки экрана.
- **Вывод «не работает» из встроенной панели.** CSR-страница не отрисовалась у
  наблюдателя, у пользователя всё работает — и наоборот.
- **Состояния «потом».** Пустое состояние и ошибка не попали в план и не сделаны.
- **Моки, уехавшие в релиз.** Непомеченный мок переживает приёмку.
- **Типы, написанные руками по контракту.** Третья копия контракта, расходится
  молча (R2.3).

## Корпоративные конвенции кода

Если у команды есть собственный стандарт написания кода и структуры проектов,
код пишется строго по нему; конвенции открытого проекта — запасной вариант.
