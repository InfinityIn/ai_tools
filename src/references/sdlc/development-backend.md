# Разработка: бэкенд — дельта артефактов этапа

Справочник этапа «Разработка», профиль бэкенда. Рабочий контур — `develop-it`
(`src/process/develop-it/SKILL.md`); регламенты — R2.3 (контракты и генерация),
R2.4 (модель данных и миграции), R3.4 (обработка отказов), R5.2 (миграции в
проде), см. `docs/regulations/README.md`.

Общие артефакты и критерии этапа — в `development.md`. Здесь только **дельта
бэкенда**: она ничего не отменяет, а добавляет.

## Дополнительные артефакты

| Артефакт | Где | Когда обязателен |
|---|---|---|
| Миграция схемы БД | репозиторий проекта | меняется схема |
| Замер «до» и «после» | раздел changelog | задача о производительности |
| Реестровая запись флага интеграции | реестр флагов проекта | новая интеграция |
| Раздел бэкенда в `output/changelog.md` | `output/changelog.md` | всегда |

## Контракты API — обязательство

Реализация **обязана совпасть с контрактом** из `api-contracts`. Контракт —
источник правды, а не черновик (R2.3). Изменение контракта — только возвратом на
системный анализ, с докладом владельцу. Расхождение обнаружено в реализации —
**стоп и доклад**, не подгонка. Копия контракта, написанная руками во второй
раз, расходится с первой молча: структура описывается один раз, потребители
генерируются.

## Миграции БД

- **Один head.** Перед созданием миграции проверить, что головная ревизия одна;
  две головы — развести, а не накатывать поверх (R2.4).
- **Схема идёт до кода** — отдельным коммитом, чтобы код никогда не оказался в
  проде раньше своей схемы (R5.2).
- **Совместимость назад:** миграция не ломает текущую работающую версию —
  добавление вместо переименования, удаление отдельным поздним шагом.
- `lock_timeout` выставлен; длинная блокировка не валит прод (R5.2).
- Статусы и периоды — перечисления в БД, а не свободные строки; `NULL` не
  используется как состояние (R2.4).
- **Прод-БД — только чтение.** Ремонтные SQL оформляются отдельными скриптами и
  выполняются после проверки и явного решения владельца, не из сессии.

## Производительность

- **Замер до кода** — read-only (`EXPLAIN ANALYZE`, профиль, метрики) и **замер
  после — тем же методом**, иначе сравнивать нечего.
- **Постановки протухают.** Если замер опровергает постановку (узкое место в
  другом месте или его уже нет) — остановиться и доложить, не рефакторить вслепую.
- Одинокая цифра — гипотеза, а не факт: ключевое число подтверждается вторым
  независимым способом. Вывод без цифры не существует.

## Интеграции с внешними системами

- Каждая новая интеграция — **за флагом или конфигом**, с предусмотренной
  деградацией: таймаут, ограниченные ретраи, поведение при недоступности.
- Флаг заводится **с владельцем и датой смерти**; удаление — в два шага.
- Секреты — только из конфигурации окружения; в коде, логах и тестах их нет.
- Ошибка интеграции **видна**: метрика и явная отметка отказа, а не тихий
  пропуск (R3.4).

## Критерии приёмки дельты

- Ответы эндпоинтов совпадают с контрактом по полям, типам и **кодам ошибок**.
- Головная ревизия миграций одна; миграция накатывается и откатывается на копии.
- Для задачи о производительности в changelog есть **две цифры одним методом**.
- Новая интеграция выключаема флагом, и выключенное состояние проверено.
- В диффе нет секретов и нет проглоченных исключений.

## Типовые ошибки

- **Две головы миграций.** Ветки разошлись, накат поверх — прод встаёт.
- **Код в проде раньше схемы.** Деплой прошёл, таблицы ещё нет.
- **Переименование колонки одной миграцией.** Старая версия приложения падает
  до конца выкатки.
- **Замер только «после».** Улучшение недоказуемо.
- **Интеграция без флага.** Отключить нечем, откатывать приходится деплоем.
- **Подгонка под факт.** Бэкенд «поправлен» под то, что уже отдаёт стенд, а
  контракт остался прежним — дефект переехал к потребителю.

## Корпоративные конвенции кода

Если команда держит собственный стандарт написания кода и структуры сервисов,
код пишется строго по нему, а конвенции открытого проекта — запасной вариант.
Импортированный корпоративный стандарт (чистая архитектура, структура сервиса и
UseCases, конвенции C#, документирование) — в
`development/corporate-code-standard.md` рядом с этим файлом.
