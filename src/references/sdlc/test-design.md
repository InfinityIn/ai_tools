# Тест-дизайн — артефакты этапа

Справочник этапа «Тест-дизайн», стадия 06. Этап частично идёт через
**корпоративный контур**: шаблон тест-кейса и система управления тестированием
(см. раздел «Корпоративный контур» ниже). Рабочий контур — `develop-it`
(`src/process/develop-it/SKILL.md`); регламенты — R4.1 (пирамида тестов и
обязательные ярусы на PR), R4.3 (сторожа и мутации), дополнительно R4.7
(мутационное тестирование), см. `docs/regulations/README.md`.

Этот файл описывает, **что должно быть на выходе этапа**. Как вести сессию —
в профильном скилле, не здесь.

## Вход

Требования и структура тест-документации из стадии 05 (`test-docs.md`), ТЗ на
постановку и контракты API. Артефакты предыдущей стадии читаются **напрямую из
её `output/`**, а не копированием. Без `test-docs-structure.md` генерацию
тест-кейсов не начинать — группировать будет не по чему.

Артефакты строятся **последовательно**: каждый следующий опирается на предыдущий.

## Как считаются граничные значения

- **числовые параметры** — минимум − 1, минимум, минимум + 1, номинал,
  максимум − 1, максимум, максимум + 1;
- **строки** — пустая, короткая, номинальная, длинная, спецсимволы, юникод;
- **булевы** — `true`, `false`;
- **даты** — прошлое, сегодня, будущее, `null`;
- **коллекции** — пустая, один элемент, предельный размер, превышение.

## Методика CRUDR

Каждая операция изменения (C, U, D) немедленно проверяется операцией чтения (R):

- **CR** — базовая проверка создания;
- **UR** — базовая проверка обновления;
- **DR** — базовая проверка удаления;
- **CRUDR** — полный жизненный цикл (основной сценарий);
- **CRURDR** — двойное изменение.

Длинные последовательности из шести и более операций — только при
необходимости: конкурентность, транзакции, сложная бизнес-логика.

## План тестирования

Стратегия: область, **ярусы пирамиды** (что обязательно с первого дня, что
включается позже), что автоматизируется и что остаётся ручным, риски (R4.1).
Ярус, не запускаемый в гейте, тестом не является — у каждого яруса должен быть
ответ на вопрос «какой джоб меня исполнит» (R4.2, R4.3).

## Критерии приёмки этапа

- **Каждое требование покрыто** хотя бы одним тест-кейсом; матрица трассировки
  показывает непокрытые требования явно, а не умалчивает о них.
- Таблица покрытия указывает по каждому требованию **какие техники** его
  покрывают и уровень: полное / частичное / не покрыто.
- Тест-кейсы **сгруппированы по структуре** модуль → сервис → функция из стадии
  05; у каждого кейса есть поле модуля.
- У каждого кейса: уникальный `ID`, тип (позитивный / негативный / граничный),
  уровень (unit / integration / e2e / manual), приоритет, предусловия, шаги,
  ожидаемый результат, связь с требованием.
- Граничные значения посчитаны для **всех** параметров из требований, а не для
  выбранных «на глаз».
- Экспорт CSV валиден: обязательные поля заполнены, `ID` уникальны, кавычки
  закрыты, число столбцов совпадает с заголовком, кодировка соответствует
  регламенту экспорта.

## Типовые ошибки

- **Тестирование «на глаз».** Кейсы придуманы без техник — покрытие случайное.
- **Плоский список кейсов.** Без группировки по структуре набор не переносится в
  систему управления тестированием и не сопровождается.
- **Кейс без связи с требованием.** Матрица трассировки разваливается, при
  изменении требования непонятно, что перепроверять.
- **Только валидные данные.** Негативные и граничные кейсы не написаны.
- **Ожидаемый результат «работает корректно».** Непроверяемая формулировка.
- **Параллельная генерация зависимых артефактов.** Классы эквивалентности,
  построенные раньше граничных значений, приходится переделывать.
- **Кейс на ярус, которого нет в гейте.** Тест существует и никогда не
  запускается (R4.3).

## Корпоративный контур

- **Шаблон тест-кейса команды** — если он есть, оформление идёт строго по нему,
  встроенный формат становится запасным вариантом.
- **Система управления тестированием** — оттуда читаются существующие кейсы для
  контекста; перенос структуры, приоритизация и распределение по тест-планам
  выполняет человек по регламенту.
- **Формат экспорта в CSV** — регламент лежит рядом:
  `test-design/test-cases-csv-format.md` (столбцы, правила экранирования,
  кодировка, импорт в TestRail / Xray / QMetry).
