# develop-it — разработка руками агентов, руководство руками оркестратора

**База:** вызови скилл `orchestrate` и работай по его скелету. Роли, скелет
процесса, правила анализа данных и формат финала — там, здесь не повторяются.
Ниже — только профиль разработки. Режим выработан на живых сессиях разработки
(июль–август 2026).

## Роли и модели — дельта к базе

- **Оркестратор сам код НЕ пишет.** Мерж, пуш, доска, память и финальная
  приёмка — только на нём.
- **Модель субагента по типу задачи**: боевой код, ревью, сложный ops — opus;
  диагностика, SQL-разведка, мелкий ops, live-приёмка — sonnet. Выше Opus не
  поднимать никогда.
- Задачи — **строго последовательно**, один агент за раз (ждать завершения).
  Параллельно можно только бухгалтерию оркестратора (доска, доки). Исключение —
  team-режим ниже, где параллельность допустима при непересекающихся файлах
  (R7.5).

## Выбор режима исполнения — решает оркестратор, владельца не спрашивать

По умолчанию — субагенты последовательно (цикл ниже). **Agent Team поднимать
самостоятельно**, только если верно ВСЁ разом:

- пачка режется на ≥2 куска **без пересечения по файлам/модулям**;
- каждый кусок — самостоятельная задача на часы (не правка пары файлов);
- сессия свежая: teams не переживают `/resume`.

Правила team-режима: teammates — model не выше Opus; каждому — свой worktree
и ветка по шагу 1 цикла (общий рабочий каталог — иначе перезаписи); ревью,
мерж, пуш и live-приёмка — по тому же циклу, ревьюер по-прежнему отдельный
и независимый; стоимость линейна по числу teammates — для мелочи не поднимать.
Требуется `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` в env (`~/.claude/settings.json`);
если флага нет в текущей сессии — молча работать субагентами, а в финале
отметить, что team-режим был бы уместен. Выбранный режим и почему — одной
строкой в блоке решений финала (см. `orchestrate`).

## Цикл одной задачи / пачки задач

1. **Разработчик-агент** (opus): отдельный worktree + ветка от main
   (`git worktree add .claude/worktrees/<slug> -b feat/<slug> main`).
   **TDD**: красный тест → код → зелёный; для perf-задач — **замер на проде ДО
   кода** (EXPLAIN ANALYZE / \timing, read-only) и после. Коммиты в ветку с
   `Co-Authored-By: <модель сессии> <noreply@anthropic.com>`, **НЕ пушить**,
   worktree не удалять (для ревью). Отчёт: корень проблемы, что сделано,
   красный→зелёный по каждому тесту, что НЕ сделано и почему.
   Если замер опровергает постановку — остановиться и
   доложить варианты, не рефакторить вслепую (постановки протухают за дни).
2. **Независимый ревьюер-агент** (opus, другой агент): читает дифф целиком,
   сам прогоняет тесты/сборку, проверяет честность тестов **мутациями**
   (тест обязан падать на заведомо сломанном коде). Вердикт: «мержить» /
   «мержить после правок» (список: severity, файл:строка, вход→неверный выход) /
   «не мержить».
3. **Правки** — тому же разработчику, каждая с красным тестом; повторное ревью
   дельты тем же ревьюером. Финальный гейт — ревьюер.
4. **Мерж и пуш — только оркестратор**: `--no-ff` с содержательным сообщением.
   Помнить: если деплой-воркфлоу push-триггерные, мерж в main = деплой.
5. **Live-приёмка после деплоя**: дождаться деплой-джобов (например, journalctl
   раннера по SSH — gh локально может отсутствовать), затем прод живьём: API,
   логи, латентность и **экран целиком**. CSR-страницы проверять ТОЛЬКО в
   реальном браузере (claude-in-chrome): встроенная браузер-панель без
   отображения не композитит кадры и не запускает data-запросы — страница
   выглядит пустой при живом проде (урок «ложного отката»).
6. **Закрытие**: карточка на доске → Solved с фактами проверки (цифры, коммиты);
   follow-up находки — отдельными карточками; в конце сессии обновить память и
   проектные заметки; итоговое резюме владельцу — финал по `orchestrate`.

## Жёсткие правила

- Прод-БД — **только чтение**; ремонтные SQL — отдельными скриптами, применение
  после ревью и решения владельца. Остальные правила работы с данными и
  доказательствами — см. `orchestrate`, раздел «Анализ данных».
- Перед откатом на проде — решающий эксперимент во **второй независимой среде**.
- «**Green helper is not a green feature**»: тесты фиксируют call-site путь
  (реальный путь запроса/пользователя), а не только хелпер.
- «**Красный тест ≠ сломанный код**»: сначала проверить, не отменено ли
  утверждение теста сознательно.
- Изменение прод-состояния — только когда доказательства подтверждают именно
  это действие.
- Ops-скрипты и heredoc — ASCII-only (Windows-консоль cp1251).

## Регламенты

Каталог и индекс: `docs/regulations/README.md` в репозитории ai_tools
(https://github.com/InfinityIn/ai_tools). Ссылки — по коду.

- **R3.1** — цикл фичи: spec → красный тест реального пути → код → ревью →
  деплой → телеметрия под SLO → DoD.
- **R3.2** — малые изменения: размер PR, один класс на PR, запрет «поправь, что
  заметишь» без воспроизведённого отказа.
- **R3.5** — гигиена веток и рабочих деревьев агентов: worktree на агента,
  `git status` каждого дерева перед мержем, общий чекаут.
- **R4.2** — гейт CI: безусловный, без `paths:` для тестов, allowlist = 0.
- **R4.3** — сторожа и мутации: сторож обязан доказать себя мутацией.
- **R4.4** — код-ревью: независимый ревьюер, фиксированный список аспектов,
  вердикт из трёх.
- **R4.5** — Definition of Done: класс и сторож названы, телеметрия под SLO,
  документ обновлён, приёмка на проде.
- **R7.5** — параллелизм агентов: WIP-лимит, один модуль на агента,
  независимость по файлам.

Проектные ловушки — в `docs/` проекта, ссылка из `CLAUDE.md`; здесь только
шаблон, потому что репозиторий публичный. Проверяйте их актуальность перед

  до кода».

  перебивают тестовые переменные, дев-БД против прод-БД.
